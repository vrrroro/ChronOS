# ChronOS — Architecture

System design reference. Covers component responsibilities, module boundaries, data flow, and interaction contracts. For *why* these decisions were made, see `PRD.md` §2 and §4. For dashboard visuals, see `EDRD.md`. For build rules, see `AGENTS.md`.

---

## 1. System overview (updated 2026-08-23 — architecture pivot)

**This section describes the current (post-pivot) architecture.** ChronOS was originally three subsystems connected only by files on disk (engine → JSON → web dashboard, plus analysis). The dashboard was replaced with a native Qt/QML GUI that links the engine **in-process** — an explicit, logged deviation from the original file-boundary-only contract, made specifically for the interactive GUI. The CLI + JSON file path still exists unchanged, for `analysis/`.

```
┌──────────────────┐
│  chronos_core     │  (static lib: schedulers, simulator, workload I/O)
│  (C++17)          │
└──────────────────┘
      │        │
      │        └──────────────────────┐
      ▼                               ▼
┌──────────────────┐  results/*.json  ┌───────────────────┐
│   chronos (CLI)   │ ────────────────▶│  analysis.py        │
│                   │                  │  (Python)           │
└──────────────────┘                  └───────────────────┘
      ▲
      │ in-process call (ChronosBridge), no JSON round-trip
      │
┌──────────────────┐
│  chronos_app       │  native Qt 6 / QML desktop GUI
│  (C++ + QML)        │
└──────────────────┘
```

The practical consequence for implementation: **the JSON schema (Section 4 below) is still the contract for the CLI/analysis path**, and **the `Scheduler`/`Workload`/`SimulationResult` C++ types (Section 3.2/4.1) are the contract for the GUI path**. `chronos_core` exists precisely so both paths call identical scheduling logic — never reimplement scheduler/workload-loading behavior separately for the GUI.

| Component | Language | Responsibility | Does NOT do |
|---|---|---|---|
| `engine/` | C++17 | `chronos_core` (static lib): scheduling logic, tick loop, JSON I/O. `main.cpp`: CLI entry point only. | Render anything; know about the GUI or dashboard |

Everything except `main.cpp` builds into `chronos_core` (a CMake `STATIC` library target). `chronos` (the CLI) and `chronos_app` (the GUI, Section 5 below) both link `chronos_core` and call the same `loadWorkload()`/`makeScheduler()`/`runSimulation()` functions — this split exists specifically so the two consumers can never drift into subtly different scheduling behavior.

### 3.2 Scheduler interface (the internal contract every algorithm implements)

Every scheduler — FCFS through AARS — implements the same shape, so `simulator.cpp` never needs to know which algorithm is active:

```cpp
class Scheduler {
public:
    virtual ~Scheduler() = default;

    // Called once per tick. Given the current ready queue and tick number,
    // return the PID to run next (or -1 if nothing is ready).
    virtual int selectNext(std::vector<Process>& readyQueue, int currentTick) = 0;

    // Called once per tick after selectNext, for schedulers with a
    // time-quantum concept (RR, MLFQ, AARS). Return ticks remaining
    // in the current process's slice, or -1 if not quantum-based.
    virtual int currentQuantum(const Process& running) const { return -1; }

    // Called every tick while a process is mid-slice. true = end the slice
    // now and call selectNext() this tick. Default false. (Added 2026-10-22.)
    virtual bool shouldPreempt(const Process& running, const std::vector<Process>& readyQueue,
                               int currentTick) { return false; }

    // For logging/dashboard: explain the selectNext decision just made.
    virtual DecisionLog explainLastDecision() const = 0;

    virtual std::string name() const = 0;
};
```

**`shouldPreempt` (added 2026-10-22)** is the one addition since Milestone 1: MLFQ needs it so a higher queue can take the CPU mid-slice, CFS for wakeup preemption. The three-place `if` in the tick loop (§3.3, step 4) was already written for it. Because the default returns false, the five original schedulers never reach the scheduling block mid-slice and their output is byte-identical (checked: all 40 original runs, ignoring the new additive `nice` field). It is also exactly the hook issue #5 (arrival preemption for AARS) needs.

Schedulers may keep their own per-PID state (MLFQ: level + allotment used; CFS: vruntime + weight). Neither needs a signal from the simulator about slice ends: each reads CPU used off `burstTime − remainingTime` whenever it is called and folds in the difference.

Rationale: `simulator.cpp` (Section 3.3) is written once, against this interface. Adding MLFQ later, or retuning AARS, never touches the simulator core — only the scheduler's own `.cpp` file. This is what makes the Milestone 1 → 3 split in the PRD safe: the simulator loop doesn't change when a new scheduler is added, so proving it correct once (against FCFS, the simplest case) proves the loop itself is trustworthy for every algorithm after.

### 3.3 The tick loop (`simulator.cpp`)

This is the heart of the engine — one function, run once per simulation:

```
function runSimulation(workload, scheduler):
    tick = 0
    readyQueue = []
    waitingQueue = []      # processes doing I/O (if modeled)
    newQueue = sorted(workload.processes by arrivalTime)
    completed = []
    ganttLog = []
    decisionLog = []
    runningProcess = null
    quantumRemaining = 0

    while completed.size < workload.processes.size:
        # 1. Admit newly-arrived processes
        move all processes from newQueue with arrivalTime == tick into readyQueue
        set their state = READY

        # 2. Update waiting stats for everyone still in readyQueue
        for p in readyQueue: p.waitingTime += 1

        # 3. Ask the behavior analyzer to (re)classify anyone whose burst history changed
        behaviorAnalyzer.updateClassifications(readyQueue)

        # 4. Scheduling decision
        if runningProcess == null or quantumRemaining == 0 or scheduler.shouldPreempt(...):
            nextPid = scheduler.selectNext(readyQueue, tick)
            if nextPid != runningProcess.pid:
                record context switch
                if runningProcess != null: push runningProcess back to readyQueue (state = READY)
                runningProcess = remove nextPid from readyQueue
                runningProcess.state = RUNNING
                if runningProcess.responseTime == -1: runningProcess.responseTime = tick - runningProcess.arrivalTime
            quantumRemaining = scheduler.currentQuantum(runningProcess)
            decisionLog.append(scheduler.explainLastDecision())

        # 5. Execute one tick
        if runningProcess != null:
            extend or append ganttLog segment for runningProcess at this tick
            runningProcess.remainingTime -= 1
            quantumRemaining -= 1

            # 6. Check completion
            if runningProcess.remainingTime == 0:
                runningProcess.completionTime = tick + 1
                runningProcess.turnaroundTime = runningProcess.completionTime - runningProcess.arrivalTime
                runningProcess.state = TERMINATED
                completed.append(runningProcess)
                behaviorAnalyzer.recordCompletedBurst(runningProcess)
                runningProcess = null

        tick += 1

    return buildResultJson(ganttLog, decisionLog, completed, summaryStats)
```

Key invariants this loop must preserve (verify these first when debugging any scheduler):

- A process's `waitingTime` only increments while it sits in `readyQueue`, never while `RUNNING` or `TERMINATED`.
- `responseTime` is set exactly once, the first time a process is ever scheduled.
- Every tick the CPU is busy produces exactly one Gantt entry (or extends the previous one if it's the same PID — don't emit one JSON object per tick, coalesce consecutive same-PID ticks into a single `{start, end}` range).
- A context switch is counted only when the running PID actually changes, not on every scheduling decision (re-selecting the same process that's already running is not a switch).

### 3.4 Behavior analyzer (`behavior_analyzer.h/.cpp`)

Stateless with respect to the simulator loop — it only reads/writes fields already on the `Process` struct (`burstHistory`, `ioEvents`, `predictedClass`). Two entry points:

- `recordCompletedBurst(Process&)` — called when a process finishes a burst (either completes entirely or is preempted); appends the burst length to `burstHistory` (capped at last 5, per PRD §6.3).
- `updateClassifications(vector<Process>&)` — recomputes `predictedClass` for every process in the given vector using the rule in `PRD.md` §6.3 (one completed burst is enough; CPU consumed so far counts as CPU-bound evidence even mid-burst).

**Revised 2026-08-24 (issue #3):** `simulator.cpp` calls `updateClassifications` in three places, not one — on `readyQueue` each tick, on the currently-running process wrapped in a single-element vector (`justRunning`), and once more on the just-finished process at completion. The running process is held *outside* `readyQueue` while dispatched, so classifying only the queue means the one process actually accumulating evidence (the one running right now) is the one never being looked at — that was the root cause of the original mostly-`UNKNOWN` bug, not the threshold values.

Only `aars.cpp` reads `predictedClass` and `avgBurstHistory` for scheduling decisions — FCFS/SJF/RR/Priority ignore behavior analysis for scheduling purposes, but the simulator still classifies every process under every algorithm so `processStats[].class` (§4.3) and the GUI's `CLASS` badge are populated regardless of which algorithm ran.

### 3.5 AARS-specific internals (`aars.cpp`)

`AARSScheduler::selectNext` computes `Score(p, tick)` for every process in `readyQueue` per the formula in `PRD.md` §6.1, using the analyzer's `predictedClass`/`avgBurstHistory` and the process's own `waitingTime`/`responseTime` fields — no additional state beyond what's already on `Process`. `currentQuantum` looks up the table in `PRD.md` §6.4 keyed on `predictedClass`. `explainLastDecision` must return every candidate's score and the winning process's reason tags (see Section 4.3 below) — this is not optional instrumentation, it's required by the JSON schema and by the dashboard's why-panel.

### 3.5a MLFQ and CFS internals (`mlfq.cpp`, `cfs.cpp`, 2026-10-22)

Full rules in `PRD.md` §6.6/§6.7. Parameters are resolved per workload by `resolveMlfq()`/`resolveCfs()` from the workload's `quantum` plus its optional `"mlfq"`/`"cfs"` blocks (`PRD.md` §5.2), so `makeScheduler()` is still the only constructor call site.

- **MLFQ** tracks `{level, used, lastConsumed}` per PID. `selectNext` accounts every ready process's new CPU into its allotment (demoting it once spent), applies the periodic boost, then picks the first process (FIFO order) at the lowest level. `shouldPreempt` applies the boost and returns true when any ready process sits in a higher queue than the running one. `currentQuantum` returns what is left of the running process's allotment at its level.
- **CFS** tracks `{vruntime, weight, lastConsumed}` per PID and a monotonic `min_vruntime`. `selectNext` updates vruntimes, places unseen processes at `min_vruntime`, builds a `std::set<(vruntime, pid)>` and takes its first element; the slice is the weighted share of the latency period. `shouldPreempt` updates the running process, places new arrivals, and preempts if the running process is ahead of one by more than the (weight-scaled) wakeup granularity.

### 3.6 JSON I/O

- Input: one workload JSON (`PRD.md` §5.2) parsed with `nlohmann/json` at startup.
- Output: one result JSON (`PRD.md` §5.3) written once, at the end of `runSimulation`, via `nlohmann/json`'s object-building API — never hand-built with string concatenation (a common source of subtly invalid JSON).
- The engine is single-purpose per invocation: one algorithm, one workload, one output file. Running "all algorithms against one workload" (for comparison) is a shell-level loop calling the binary multiple times (Section 6.2), not a feature inside the engine itself.

## 4. Data contracts (the schemas everything else depends on)

These are reproduced from `PRD.md` §5 because they are the single most important interface boundary in the system — any change here must be made in both documents at once, plus every reader (dashboard, analysis.py).

### 4.1 Process struct (in-memory, engine only — not serialized directly)

See `PRD.md` §5.1 for the full struct. Key point for architecture: this struct is engine-internal state. It is never serialized as-is; the result JSON's `processStats` array (4.3 below) is a deliberately reduced projection of it, and `gantt`/`decisionLog` extract only the fields each needs.

### 4.2 Workload JSON (engine input)

See `PRD.md` §5.2. Consumed only by the engine (`main.cpp` reads the `--workload` path). Dashboard and analysis never read workload files directly — they only ever see engine *output*.

### 4.3 Result JSON (engine output → dashboard + analysis input)

See `PRD.md` §5.3 for the full shape. Field-by-field ownership:

| Field | Written by | Read by |
|---|---|---|
| `algorithm`, `workloadName` | engine (from CLI args / workload file) | dashboard (top bar), analysis (grouping key) |
| `gantt[]` | `simulator.cpp` tick loop | dashboard (Gantt chart, EDRD §5.2) |
| `decisionLog[]` | `scheduler.explainLastDecision()` each tick | dashboard (why-panel, EDRD §5.4) |
| `processStats[]` | computed at completion, per process | dashboard (ready queue history, process HUD — EDRD §5.10), analysis (per-process detail if needed) |
| `summary` | computed once, at end of `runSimulation` | dashboard (top-bar stat tiles), analysis (comparison table/charts — this is the primary field analysis.py consumes) |

`analysis.py`'s main job is: read N result JSONs' `summary` blocks, one per algorithm (same `workloadName`), and produce the comparison table + charts in `PRD.md` §8.2. It does not need `gantt` or `decisionLog` at all — those exist purely for the dashboard.

**Widened 2026-08-24:** `processStats[]` entries gained `arrivalTime`, `burstTime`, `contextSwitches`, and `class` (additive, see `PRD.md` §5.3). This exists specifically for the GUI's `ProcessHud` (EDRD §5.10) — hovering a finished process bar needs to describe it (how long it ran, when it arrived, how it was classified) without the GUI cross-referencing the original workload file. `analysis.py` should read these fields rather than recompute them.

### 5.2 `ChronosBridge` — the in-process engine link

`ChronosBridge::runSelectedSimulation()` calls `loadWorkload()` + `makeScheduler()` + `runSimulation()` from `chronos_core` directly (Section 3.6's C++ API, not the JSON file), storing the resulting `SimulationResult` in memory. Every other bridge method is a **pure function of `(m_result, tick)`**, ported 1:1 from the original web dashboard's `app.js` derivation helpers (`ticksRunUpTo`, `runningSegmentAt`, `lastDecisionAt`, `contextSwitchesUpTo`, `estimateAgingBonus`, the `processColor` palette cycle, and `buildProcessMeta`'s arrival/burst back-derivation from `processStats`) before that file was deleted — the underlying state-reconstruction-from-logs principle described in the old Section 5.2 above still holds, just implemented in C++ instead of JS:

```cpp
QVariantList readyQueueAt(int tick) const;   // EDRD §5.3 rows, in each algorithm's own pick order
QVariantMap  whyPanelAt(int tick) const;     // EDRD §5.4 reasons + score breakdown (idle-aware)
QVariantMap  agingAt(int tick) const;        // EDRD §5.5 — per-algorithm aging rule + entries
QVariantList processTickerAt(int tick) const; // new — per-process completion progress
int          cpuUtilizationAt(int tick) const;
int          contextSwitchesAt(int tick) const;
```

**Revised 2026-10-22:** these are now pure functions of a private `Run` (result + per-PID meta + the workload + AARS weights it ran with) rather than of loose members, so the bridge can hold the dashboard's run and the compare screen's two runs side by side. The `cmp*` methods (`runComparison`, `cmpGanttSegments(side)`, `cmpTickerRowAt`, `cmpDoneAt`, `cmpSwitchesAt`, the `comparison` property) are the same derivations over `m_cmp[0]`/`m_cmp[1]`. Three behaviours were fixed at the same time: idle ticks (a decision with `chosen == -1`) no longer count as context switches or show as "P-1" in the why-panel; the ready queue also lists processes that arrived after the last decision; and the aging panel applies the running algorithm's own aging rule instead of AARS's defaults for every algorithm.

There is no separate "ready queue over time" array in `SimulationResult` — same deliberate simplification as before: state-at-a-tick is reconstructed from `gantt[]`/`decisionLog[]`/`processStats[]`, which is why the JSON schema (Section 4) didn't need to change for the GUI to exist.

### 5.3 Playback loop

Implemented as a QML `Timer` inside `Dashboard.qml`, driving a local `currentTick` property that every panel binds to (so panels re-evaluate automatically via normal QML property-binding dependency tracking — no manual "render()" call needed, unlike the old JS version):

```qml
readonly property real ticksPerSecond: Theme.baseTicksPerSecond * speed

Timer {
    interval: Math.max(16, 1000 / root.ticksPerSecond)
    running: isPlaying
    repeat: true
    onTriggered: currentTick = Math.min(currentTick + 1, maxTick)   // auto-pauses at maxTick
}
```

**Revised 2026-08-24b (explicit user request):** `Theme.baseTicksPerSecond` is `0.6`, not the `2` shown in early drafts of this section — this is a teaching instrument, and at 2 decisions/second the why-panel changed faster than its own verdict line could be read. The 0.5×/1×/2×/4× `speed` multiplier is unchanged; a slow default costs a skimmer one click on the 4× button. Nothing hardcodes a tick interval — always read `Theme.baseTicksPerSecond`.

`stepForward`/`stepBack`/`resetRequested`/`scrubRequested` (from `PlaybackControls.qml`) all just set `currentTick` directly and set `isPlaying = false` first — structurally identical control flow to the old `pause(); state.currentTick = ...; render(state)` pattern, just via QML property assignment instead of an explicit render call.

## 6. Analysis internals (`analysis/analysis.py`)

**Built 2026-10-22.** `analysis/analysis.py` (stdlib only; matplotlib optional for `--charts`) and `analysis/run_all.py` (runs every algorithm × workload through the CLI into `results/`). Views: the default all-algorithms table per workload, `--pair A B` (the GUI's head-to-head verdict, workload by workload), and `--versus A B C…` (where A beats *every* other listed algorithm, and where it loses to at least one). Writes `analysis/output/report.md`, `comparison.csv`, and with `--charts` four PNGs styled per EDRD §7.2. Metric definitions mirror `engine/comparison.cpp`; the two were cross-checked verdict by verdict (432/432 identical).

### 6.1 Responsibilities

1. Load a set of result JSONs (one per algorithm, same workload).
2. Extract each one's `summary` block into a pandas DataFrame (`algorithm` as index, metrics as columns).
3. Write a comparison table (CSV + Markdown).
4. Render the charts specified in `PRD.md` §8.2 using matplotlib, styled per `EDRD.md` §7.2 (dark background, neon palette, JetBrains Mono).

### 6.2 How comparisons actually get generated

`analysis.py` does not invoke the C++ engine itself — a separate small script/shell loop (e.g. `scripts/run_all.sh` or a `runner.py`) is responsible for calling the engine binary once per algorithm against one workload, collecting the output paths, and handing them to `analysis.py`:

```
for algo in fcfs sjf rr priority mlfq aars:
    ./build/engine/chronos --algorithm $algo --workload workloads/mixed.json --out results/mixed_$algo.json

python3 analysis/analysis.py results/mixed_*.json
```

Keeping the "run everything" orchestration outside both the engine (which stays single-purpose) and `analysis.py` (which stays a pure reader) is what lets each piece be tested in isolation — you can hand `analysis.py` three hand-crafted fake result JSONs and verify the chart/table logic without ever invoking the C++ binary.

## 7. Cross-cutting: the decision log as shared infrastructure

The `decisionLog` (defined once, in Section 4.3) is deliberately reused for three different consumers instead of building three separate logging mechanisms (per `PRD.md` §11):

1. **The dashboard's why-panel** reads it live, per-tick, from the loaded JSON.
2. **`logs/scheduler.log`** is a human-readable text rendering of the same entries, written by the engine alongside the JSON, for terminal debugging and for quoting from during a viva.
3. **Regression testing** — built 2026-10-22 as `tests/run_tests.py` (see `PRD.md` §10). The edge-case tests in `PRD.md` §10 can assert against specific `decisionLog` entries (e.g. "at tick 14, P1 should be chosen with reason tag `aging_bonus`") rather than only checking final summary stats, which makes test failures much easier to diagnose.

Building this once, correctly, in the engine (Section 3.5) pays for itself across all three uses — it is the single highest-leverage piece of infrastructure in the whole system, and worth getting right before moving past Milestone 1.

## 8. Build & run topology

```
CMakeLists.txt   → chronos_core (static lib)
                     ├─▶ chronos      (CLI)      build/engine/chronos.exe
                     └─▶ chronos_app  (Qt6 GUI)   build/app/chronos_app.exe
analysis/         → run directly with `python3 analysis/analysis.py <files>`
```

`chronos_app` only builds if Qt6 (Core/Gui/Qml/Quick) is found via `find_package` — if it's missing, CMake configure just skips that target with a message, the CLI still builds. The GUI links `chronos_core` at compile time (Section 5.2); the CLI and `analysis/` are only coupled via the JSON files in `results/` at runtime, same as before. See `AGENTS.md` for exact commands, including the `CMAKE_PREFIX_PATH` Qt6 needs on this machine.

## 9. Extension points (where future work plugs in, without restructuring)

| Future addition | Where it plugs in | What it must NOT touch |
|---|---|---|
| ~~MLFQ (Milestone 3)~~ | **Done 2026-10-22**, with CFS — `schedulers/mlfq.cpp`, `schedulers/cfs.cpp`. Needed one additive interface hook (`shouldPreempt`, §3.2) and one additive JSON field (`processStats[].nice`) | — |
| Real pthreads (stretch, PRD §6.5) | A parallel `simulator_threaded.cpp`, separate binary target | The primary JSON-producing `simulator.cpp` path — must stay isolated so a threading bug can't break the main deliverable (per `AGENTS.md`) |
| ~~Local server for a live "Run" button~~ | Superseded — `chronos_app`'s in-process `ChronosBridge` link already does this natively, no server needed | — |
| Fairness index (stretch, PRD §6.5) | New field in `summary` (§4.3), computed at end of `runSimulation` from existing `processStats` | Nothing — purely additive to the schema |
| Large-scale benchmark mode (stretch) | New CLI flag / mode in `main.cpp` that generates a synthetic workload in-memory instead of reading one | `Scheduler` interface, JSON schema |

Every extension point above is additive to the existing module boundaries — none require restructuring the three-subsystem split in Section 1. If a future idea *would* require restructuring that split, that's a signal to slow down and re-check it against `PRD.md` §2 before building it.
